1 / Current state

현재 보호 장치와 남은 위험

현재 token 자체를 온라인 brute force로 맞히는 것은 현실적인 공격 경로가 아닙니다. 64자리 hex는 256-bit random secret이고 같은 길이일 때 constant-time 비교를 합니다. 더 큰 문제는 token 하나가 모든 기기와 모든 읽기·쓰기를 대표한다는 점입니다.

6 / Phase 2
P2

기기별 API Key와 권한 맵핑

한 기기의 key가 유출돼도 그 기기만 60초 안에 폐기하고, 사건 로그에서 어느 client인지 식별합니다.

왜
공유 token은 유출 출처 식별과 개별 revoke가 불가능합니다.
무엇
key ID, HMAC verifier, permissions, sensitivity ceiling, expiry, revoke 상태를 저장합니다.
어디서
repository auth middleware·migration·admin CLI와 각 client config에서 작업합니다.
완료
Codex·Claude·Hermes가 서로 다른 key를 쓰고 하나를 폐기해도 나머지는 정상이어야 합니다.

key 설계: raw key는 DB에 저장하지 않습니다. 공개 prefix와 256-bit random secret을 합친 뒤, server-side pepper를 사용한 HMAC-SHA-256 verifier만 저장합니다. 사용자가 외우는 password가 아니므로 random key 검증에 느린 password hash를 강제로 쓸 필요는 없습니다.

src/remote/auth.tssrc/server/app.tssrc/mcp/server.ts

인증 성공 결과에 다음 값을 넣고 request context로 전달합니다.

typescript / authenticated principal
type AuthPrincipal = {
  subject: string;
  clientId: string;
  keyId: string;
  permissions: Array<"memory:read" | "memory:write">;
  sensitivityCeiling:
    | "public"
    | "personal"
    | "confidential"
    | "legal_sensitive";
};
  • read tool은 memory:read를 요구합니다.
  • capture_event, link_source는 memory:write를 요구합니다.
  • write scope는 append-only tools에만 연결합니다. 임의 SQL·DDL 권한이 아닙니다.
  • caller가 보낸 sensitivity filter는 ceiling을 넓힐 수 없어야 합니다.

완료

한 번에 전부 배포하지 않습니다. 각 pull request는 rollback 가능한 경계를 가져야 하며, production 전환은 앞 단계의 증거를 확인한 뒤 진행합니다.

Render deploy gate: render.yaml의 autoDeployTrigger: commit을 checks가 통과한 commit만 배포하는 방식으로 바꾸는 것을 권장합니다. migration은 forward-compatible하게 작성하고 old app과 new app이 짧게 공존해도 깨지지 않아야 합니다.

13 / Incident response

사고 유형별 즉시 대응

정상 운영에서는 원격 쓰기를 유지합니다. 아래 kill switch는 침해 징후가 있는 사고 대응에만 사용하고, 원인과 무결성을 확인한 뒤 authorized write를 복구합니다.

기기 key 유출
해당 key만 revoke → 재사용 alert 확인 → 그 key의 최초 이상 시각부터 tool·result volume 조사 → 새 key 발급 → 다른 client는 유지.
공유 legacy token 유출
dual-auth가 있으면 legacy token 즉시 폐기. 아직 전환 전이면 incident mode로 writes를 잠시 차단하고 token 회전·세 client 재설정·로그 조사.
DB runtime password 유출
Network Restrictions 확인 → runtime password 회전 → Render DSN 갱신 → 기존 session 종료 → DB audit와 row integrity 확인.
DB admin DSN 유출
admin password 즉시 회전 → role/schema/RLS 변경 이력 검사 → backup/PITR 지점 확보 → migration runner secret 갱신 → runtime과 분리 재확인.
비정상 write
해당 client revoke → 필요 시 HERMES_ALLOW_REMOTE_WRITES=false incident switch → 영향 event/source 식별 → 삭제보다 archive/보존 우선 → 무결성 확인 후 writes 복구.
대량 recall 의심
client revoke와 IP 임시 차단 → result volume과 민감도 범위 계산 → 관련 credential 회전 → 필요한 법적·개인 통지 판단.
배포 후 DB 장애
새 app rollback → 이전 CIDR 목록과 runtime DSN 확인 → schema version 불일치 분석 → 침해가 아니라면 authorized append 기능 유지.

사고 때도 로그를 지우지 마십시오. service 복구 전에 request log, Render deploy event, Supabase connection/audit 증거를 보존합니다. token과 memory content를 새 증거 파일에 복제하지는 않습니다.
